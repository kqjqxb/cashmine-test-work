  What's in src/lib/money.ts:
  - Strict parsing: one regex, ^(0|[1-9]\d*)(?:\.(\d+))?$, checks every API
    string. A valid string becomes a bigint as BigInt(whole + fraction padded to
    decimals), so no JS numbers are involved anywhere.
  - User input: parseUserAmount trims whitespace and turns a comma into a dot,
    then hands off to the same strict parser. It deliberately rejects 1,000.5
    rather than guessing about thousand separators.
  - formatAmount: its output is always valid API format, so you can send it
    straight back in POST /v1/claims.
  - validateClaimAmount: checks in this order: format, then below min, then
    above available, then receive ≤ 0. It takes minAmount, available and fee as
    bigints, because API strings should be parsed once when the response
    arrives.
  - USD: values are an exact {units, scale} decimal, where the scale is the
    asset's decimals plus the price's decimals. totalUsd brings all values to
    one scale and adds them before any rounding; one test shows why this matters
    (three amounts of $0.004 add up to $0.01, but rounding each first gives
    $0.00). Rounding happens only in formatUsd, half away from zero. If any
    price is malformed, the total is null rather than a partial number.

  Things I decided that you didn't specify:
  - Signed amounts: I added parseSignedAmount, because the docs say activity
    amounts are signed (negative for reversals and claims). Your strict parser

  Recommendation: approach C, with D's "in progress" note on top. All the
  correction logic sits in one pure function, displayBalance(snapshot,
  localClaims), which takes about 10 unit tests.

  If time runs short, fall back to D alone. It's about a third of the work, it's
  honest, and it prevents the double claim. Only B is ruled out, because it is
  the trust complaint built into the app.

  Timeline the approaches share

  - t=0: POST returns 201. The claim's createdAt (call it C) is server time.
  - Within 15s: the server's next snapshot is built, at some point in (C, C+15].
  - Within 30s: Home polls every 15s, so the first snapshot that includes the
    claim reaches the screen between t≈0 and t≈30.
  - t≈20: the claim settles to completed or failed. That shows up in a snapshot
    taken after the claim's updatedAt, which reaches the screen around t≈20–50.

  A. Show server data only

  - What the user sees: the old available for up to ~30s. Then available drops
    and claiming rises. After settling, claiming drops (completed) or the amount
    moves back to available (failed).
  - Failed claim: handled correctly, but late. The amount reappears once a
    snapshot taken after the failure arrives.
  - Stale snapshot: not an issue, because nothing local can be contradicted.
  - Reload: same picture as before the reload.
  - Complaints: causes #1. A second claim is real money: the server checks
    available live, so if the balance covers it, a second claim is created. It
    avoids #2.

  B. Optimistic local deduction, replaced by the next snapshot

  - What the user sees: at t=0, available drops immediately. A poll at t≈3 can
    return a snapshot from before C, which still shows the old available, so the
    balance jumps back up. At t≈15 it drops again.
  - Failed claim: the local deduction is discarded at the next snapshot anyway,
    so a failure is invisible until snapshots show it.
  - Stale snapshot: this is exactly where it breaks.
  - Reload: the local deduction is lost. The page shows the old snapshot, and #1
    is back.
  - Complaints: solves #1 for about 3 seconds, then causes #2. This is the
    scenario from your second piece of feedback.

  C. Reconcile local claims against snapshots by server time

  The app saves each created claim locally (in localStorage, keyed by the
  token): {id, asset, amount, createdAt, status, updatedAt}. The numbers shown
  are the snapshot plus a correction:

  - If snapshot.asOf < createdAt (the snapshot predates the claim): move the
    amount from available to claiming on screen.
  - If asOf ≥ createdAt: the snapshot already includes the claim, so no
    correction is applied.
  - If the claim failed and asOf < updatedAt: move the amount from claiming back
    to available on screen, because the server already returned it.
  - Once a snapshot's asOf ≥ updatedAt for a settled claim: drop the local
    entry, since the snapshot is now the truth.

  What this looks like in practice:

  - What the user sees: at t=0, available drops and claiming rises. Every later
    snapshot either predates the claim (still corrected) or includes it (no
    correction). The numbers never go back. At t≈20, polling GET /v1/claims/{id}
    (already planned for step 5) reports completed or failed, and the screen
    updates once.
  - Failed claim: the amount returns to available on screen when the poll
    reports the failure, before any snapshot does, and the poll's failure reason
    explains why. A rise backed by a reason doesn't break trust the way an
    unexplained one does.
  - Stale snapshot: handled by design. The comparison uses only server
    timestamps (asOf vs createdAt/updatedAt), so the device clock doesn't
    matter.
  - Reload: the local entries are reloaded, so the correction survives. Claims
    made on another device appear through snapshots within about 15s.
  - Complaints: solves both.
  - Risks:
    - It assumes asOf is the exact time the snapshot was taken. If the server
      built snapshots slightly after asOf, a claim could be subtracted twice for
      one cycle. I'll clamp the shown available at ≥ 0 and use a strict >
      comparison.
    - It needs about 60 lines plus tests.

  D. Server data plus an "in progress" note and a blocked double claim

  - What the user sees: the numbers stay as the server reports them. Under the
    asset's card: "Claim of 0.5 ETH submitted — balance updates within ~30s".
    The Claim button for that asset is disabled until a snapshot with asOf >
    createdAt arrives. After that the note becomes "In progress", then
    "Completed" or "Failed: reason".
  - Failed claim: the note shows the failure and its reason as soon as the claim
    poll reports it. The amount returns to available when snapshots catch up.
  - Stale snapshot: not an issue; the numbers are only ever server data.
  - Reload: the note survives if the claim is persisted the same way as in C.
  - Complaints: solves #1 (the cause is explained and the double claim is
    physically prevented). Causes no #2. Cost: for up to 30s the headline number
    is knowingly out of date, which the note and the "Stale" label make
    explicit.

  Why C over D

  C gives both of what users want: the number reacts at once, and it never goes
  back except for a failure with a stated reason.

  The main risk is the assumption about what asOf means. Keeping D's note and
  the disabled Claim button limits the damage even if that assumption is wrong.
